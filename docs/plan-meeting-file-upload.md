# Plan: Загрузка файлов во встречу

**PRD:** [docs/prd-meeting-file-upload.md](prd-meeting-file-upload.md)
**Дата:** 2026-10-08

Решения, принятые при составлении плана:

- **Хранилище — локальный диск API.** Каталог задаётся переменной `FILES_DIR`, у e2e свой каталог в `.env.test`. Новых сервисов в docker-compose нет.
- **Удаление пользователя или встречи и их файлов.** Эндпоинта для этого в скоупе нет. Сервис файлов получает метод, который удаляет файлы владельца или встречи с диска и из БД. Будущие эндпоинты удаления вызовут его до удаления строки. E2E проверяет связку «очистка файлов + удаление пользователя через Prisma».
- **Браузер ходит в API через route handlers Next.** Обработчик читает httpOnly cookie и проксирует поток в Nest с `Authorization: Bearer`. Так токен не попадает ни в JS, ни в URL. Это пересматривает решение «Server Actions вместо route handlers» только для файлов (см. Фазу 4).
- **API-фазы (1, 3, 5) — тест-ферст.** Первая задача фазы — e2e-тесты на все её сценарии. Они пишутся до реализации, и прогон должен показать, что они красные по нужной причине: несуществующий маршрут, неверный код или тело ответа. Ошибка компиляции или падение setup — не та причина. Последняя задача — тот же набор, теперь зелёный. Красные тесты можно коммитить отдельно (`test(api): ...`): хук `pre-commit` гоняет только unit-тесты. Фронтовые фазы проверяются браузером через Playwright MCP, решение «Тесты только на API» не меняется.
- **Коммиты — Conventional Commits, по одному на логический шаг.** Каждая фаза описывает свои коммиты в блоке «Коммиты». Каждый коммит проходит хук `pre-commit` (Prettier, `pnpm lint`, `pnpm test`) и оставляет проект рабочим. Документация идёт в том же коммите, что и изменение, которое она описывает: отдельный `docs:` бывает только у правок без кода. Красный e2e-коммит — единственный, после которого `test:e2e` падает, и то только в новых тестах. Поправки после браузерной проверки оформляются как `fix(web): ...`.

## Фазы реализации

### Фаза 1: API — загрузка и список файлов (tracer bullet)

**Цель:** Файл можно загрузить во встречу и увидеть в списке через API (curl или e2e). Файл сохраняется на диск и переживает перезапуск.
**Затрагивает:** database / backend
**Задачи:**

- [ ] **Красные e2e** в `apps/api/test/files.e2e-spec.ts`: загрузка, состав и порядок списка, статус `uploaded`, 401, 404 на чужую и несуществующую встречу. Тестовые файлы пишутся в отдельный каталог из `.env.test`, и прогон его чистит. Тесты компилируются без новой Prisma-модели: данные чистятся через встречи, а файлы удаляет каскад. Прогон `test:e2e` — новые тесты красные, старые зелёные.
- [ ] Prisma-модель `MeetingFile` и миграция. Поля: id, `meetingId` (FK на `Meeting`, `onDelete: Cascade`), исходное имя, MIME-тип, размер, ключ хранения, статус (enum, по умолчанию `uploaded`), дата загрузки.
- [ ] Сервис хранения на локальном диске. Файл пишется потоком в `FILES_DIR`, а не держится в памяти целиком. Ключ хранения генерируется на сервере и не зависит от имени, которое прислал пользователь.
- [ ] Модуль `files` в Nest. `POST /api/meetings/:id/files` принимает multipart, один файл на запрос. `GET /api/meetings/:id/files` отдаёт список, новые первыми. Без токена — 401, для чужой или несуществующей встречи — 404.
- [ ] **Зелёный прогон** e2e фазы вместе со старыми. Документация: эндпоинты в README, `FILES_DIR` в `apps/api/.env.example`, `.env.test` и env-таблице `apps/api/CLAUDE.md`, PROGRESS.md.

**Когда готова:** `curl -F file=@x.pdf` во встречу владельца возвращает запись, и после перезапуска API она есть в `GET .../files`. E2E фазы, красные в её начале, теперь зелёные вместе со старыми, `pnpm lint && pnpm typecheck && pnpm test && pnpm build` чистые.

**Коммиты:**

1. `test(api): add failing e2e for meeting file upload and list` — `files.e2e-spec.ts`, `FILES_DIR` в `.env.test`, очистка тестового каталога.
2. `feat(api): add MeetingFile model and local disk storage` — схема, миграция, сервис хранения, `FILES_DIR` в `apps/api/.env.example` и env-таблице `apps/api/CLAUDE.md`.
3. `feat(api): add upload and list endpoints for meeting files` — модуль `files`, тесты зелёные, эндпоинты в README, PROGRESS.md.

### Фаза 2: Web — страница встречи со списком файлов

**Цель:** Из списка на главной открывается страница встречи с деталями и списком уже загруженных файлов.
**Затрагивает:** frontend
**Задачи:**

- [ ] Маршрут `/meetings/[id]`, server component. Показывает название, дату, длительность и участников из `GET /api/meetings/:id`. На 404 от API отдаёт `notFound()` и ничем не выдаёт, что встреча существует.
- [ ] Переход на страницу встречи с карточек списка на главной.
- [ ] Блок «Файлы»: имя, тип, размер, дата загрузки, статус, новые первыми. Пустое состояние — «Файлов пока нет».

- [ ] Документация: маршрут в README, PROGRESS.md.

**Когда готова:** С главной кликом открывается `/meetings/:id`. Файлы, загруженные через API в Фазе 1, видны в списке. Чужой id показывает «не найдено». Lint, typecheck и build чистые.

**Коммиты:**

### Фаза 3: API — лимиты, проверка типа и отсутствие «сирот»

**Цель:** Сервер сам отвергает недопустимые файлы, и прерванная загрузка не оставляет данных.
**Затрагивает:** backend
**Задачи:**

- [ ] **Красные e2e**: ровно 100 МБ проходит, 100 МБ + 1 отклоняется; каждый поддерживаемый тип принимается; `.exe` и подменённое расширение отклоняются с понятной ошибкой; 21-й файл отклоняется с сообщением о лимите; после оборванной загрузки нет ни записи, ни данных на диске. Прогон — новые тесты красные, старые зелёные.
- [ ] Лимиты. 100 МБ на файл проверяется прямо в потоке: на 100 МБ + 1 байт загрузка обрывается, ответ — 413 с понятным сообщением. 20 файлов на встречу: 21-й файл отклоняется с сообщением о лимите.
- [ ] Белый список типов из PRD. Тип проверяется по содержимому (сигнатура файла), а не по расширению или `Content-Type` клиента. Неподдерживаемый тип или подменённое расширение получают ошибку с причиной.
- [ ] Согласованность хранения. Файл сначала пишется во временный путь, запись в БД появляется только после успешной записи на диск. При обрыве соединения, превышении лимита или ошибке временный файл удаляется. Имя от пользователя хранится только в БД.
- [ ] **Зелёный прогон** e2e фазы вместе со старыми. Документация: коды ошибок в README, PROGRESS.md.

**Когда готова:** E2E фазы, красные в её начале, теперь зелёные. После оборванной загрузки каталог хранения и таблица не меняются. Lint, typecheck, test и build чистые.

**Коммиты:**

1. `test(api): add failing e2e for file limits and type checks`.
2. `feat(api): enforce file size and per-meeting count limits`.
3. `feat(api): verify file type by content signature` — если для этого добавляется зависимость, в PROGRESS.md появляется решение с причиной.
4. `feat(api): write uploads via temp file to leave no orphans` — тесты зелёные, коды ошибок в README, PROGRESS.md.

### Фаза 4: Web — загрузка с прогрессом и отменой

**Цель:** Пользователь загружает несколько файлов со страницы встречи, видит прогресс каждого и может отменить любой.
**Затрагивает:** frontend
**Задачи:**

- [ ] Route handler Next для загрузки. Он берёт JWT из httpOnly cookie и потоком проксирует тело в API с `Bearer`, не буферизуя его. Путь исключается из буферизации тела в middleware/proxy, и проверяется, что 100 МБ проходят. В PROGRESS.md в «Принятые решения» записывается, почему для файлов route handlers, а не Server Actions.
- [ ] Выбор файлов через диалог (несколько сразу) и перетаскиванием. До отправки на клиенте проверяются тип, размер (100 МБ) и лимит 20 файлов, причина отказа показывается, неподходящий файл не уходит.
- [ ] Каждый файл грузится отдельным запросом (XHR) с прогрессом в процентах и своей кнопкой «Отменить». Отмена одного файла не прерывает остальные, отменённый файл не попадает в список.
- [ ] Успешно загруженный файл появляется в списке без перезагрузки страницы. Ошибки сервера (тип, лимит) показываются у конкретного файла.
- [ ] Проверка в браузере на 1280 и 375 px в обеих темах: три файла одновременно с отдельным прогрессом, отмена одного, ошибки клиента и сервера. Проверить, что токена нет в JS страницы и в URL запросов. Затем README (маршрут прокси) и PROGRESS.md.

**Когда готова:** Три файла грузятся параллельно, у каждого свой прогресс. Отменённый файл не появляется ни в списке, ни на диске API. Файл 100 МБ + 1 байт отклоняется до отправки. Lint, typecheck и build чистые.

**Коммиты:**

1. `feat(web): add streaming upload proxy route handler` — route handler и исключение пути из буферизации. Решение о route handlers для файлов записывается в «Принятые решения» PROGRESS.md и в таблицу решений корневого `CLAUDE.md`, а прокси — в README.
2. `feat(web): add file picker with drag-and-drop and client validation`.
3. `feat(web): upload files with per-file progress and cancel` — прогресс, отмена, обновление списка без перезагрузки, ошибки сервера у файла, PROGRESS.md.
4. `fix(web): ...` — по замечаниям браузерной проверки, если они есть.

### Фаза 5: API — отдача с Range, скачивание и удаление

**Цель:** Файлы можно стримить с перемоткой, скачивать с исходным именем и удалять, не оставляя данных.
**Затрагивает:** backend
**Задачи:**

- [ ] **Красные e2e**. Скачанный файл побайтно совпадает с загруженным, имя с кириллицей и пробелами корректно в `Content-Disposition`. Range из середины файла возвращает 206 с нужным фрагментом. Удаление ведёт к 404 в списке и по прямой ссылке. Все эндпоинты файлов без токена отвечают 401, на чужую встречу или файл — 404. Файл читается после пересоздания приложения. После очистки и удаления пользователя через Prisma в хранилище не остаётся данных. Прогон — новые тесты красные, старые зелёные.
- [ ] `GET /api/meetings/:id/files/:fileId/content` отдаёт файл потоком с поддержкой HTTP Range (`206`, `Accept-Ranges`, `416`). `Content-Type` берётся из проверенного типа. Видео, аудио, PDF и изображения отдаются `inline`, остальное — `attachment` (`?download=1` даёт `attachment` для любого файла). В `Content-Disposition` есть `filename*` (RFC 5987), чтобы не ломались кириллица, пробелы и `../`.
- [ ] `DELETE /api/meetings/:id/files/:fileId` удаляет запись и данные на диске. После этого и список, и прямая ссылка отвечают 404.
- [ ] Метод сервиса файлов, который удаляет все файлы встречи или владельца с диска и из БД. Его вызывают будущие эндпоинты удаления встречи и аккаунта, а строки в БД добивает каскад.
- [ ] **Зелёный прогон** e2e фазы вместе со старыми. Документация: эндпоинты в README, PROGRESS.md.

**Когда готова:** E2E фазы, красные в её начале, теперь зелёные — все сценарии PRD для API покрыты и проходят вместе со старыми. `pnpm lint && pnpm typecheck && pnpm test && pnpm build` и `test:e2e` чистые.

**Коммиты:**

1. `test(api): add failing e2e for file download, range and delete`.
2. `feat(api): stream file content with range support` — отдача, `Content-Disposition`, эндпоинт в README.
3. `feat(api): delete meeting files from storage and database` — `DELETE`, метод очистки файлов встречи и владельца, тесты зелёные, README, PROGRESS.md.

### Фаза 6: Web — просмотр, скачивание и удаление

**Цель:** На странице встречи запись воспроизводится с перемоткой, PDF и изображения открываются в браузере, файл можно скачать и удалить.
**Затрагивает:** frontend
**Задачи:**

- [ ] Route handler Next для отдачи файла. Он проксирует поток из API, пробрасывает заголовок `Range` и отвечает со статусом и заголовками API (`206`, `Content-Range`, `Content-Disposition`). Аутентификация — по cookie, без токена в URL.
- [ ] Плеер для видео и аудио на странице встречи, перемотка в середину работает без полной загрузки. PDF и изображения открываются для просмотра. Для `docx`, `pptx`, `xlsx`, `txt` и `md` — только скачивание.
- [ ] Кнопка «Скачать»: файл сохраняется с исходным именем.
- [ ] Удаление с подтверждением в модальном окне. Удалённый файл пропадает из списка без перезагрузки.
- [ ] Итоговая проверка в браузере на 1280 и 375 px в обеих темах: загрузка, прогресс, отмена, ошибки, плеер и перемотка, просмотр PDF и изображения, скачивание, удаление, пустое состояние, токен не виден в JS и URL. Полный прогон `pnpm lint && pnpm typecheck && pnpm test && pnpm build` и `test:e2e`. Финальное обновление README и PROGRESS.md: пункт «Файлы во встрече» переносится в «Сделано».

**Когда готова:** Все критерии готовности PRD выполнены и проверены в браузере. Документация актуальна.

**Коммиты:**

1. `feat(web): add file content proxy with range forwarding` — route handler, README.
2. `feat(web): add media player and pdf and image preview`.
3. `feat(web): add file download and delete with confirmation`.
4. `fix(web): ...` — по замечаниям итоговой браузерной проверки, если они есть.
5. `docs: mark meeting file upload as done` — «Файлы во встрече» переносится из «Дальше» в «Сделано» PROGRESS.md, PRD получает статус Done.
